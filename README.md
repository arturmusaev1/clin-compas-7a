# Клинический компас

Демонстрационный прототип цифрового помощника для сопровождения пациента с тревожной и депрессивной симптоматикой. Кабинеты врача и пациента имеют разные интерфейсы и запускаются независимо.

Проект состоит из трех независимых сервисов:

- `doctor-ui` — кабинет врача на React (`http://localhost:5173`)
- `patient-ui` — кабинет пациента на React (`http://localhost:5174`)
- `backend` — API на Flask и база SQLite (`http://localhost:5000`)

Все данные в прототипе вымышлены. Алгоритмы оценки являются демонстрационными и не предназначены для принятия реальных медицинских решений.

## Быстрый запуск без Docker

Понадобятся Python 3.12+ и Node.js 20+.

### API

```powershell
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python app.py
```

### Кабинет врача

```powershell
cd doctor-ui
npm install
npm run dev
```

### Кабинет пациента

```powershell
cd patient-ui
npm install
npm run dev
```

## Запуск через Docker

После установки Docker Desktop достаточно выполнить `docker compose up --build`. React собирается внутри многоступенчатых Docker-образов, поэтому в контейнер всегда попадает актуальный код из `src`, а не ранее созданная локальная папка `dist`.

На текущем компьютере можно использовать готовые скрипты из корня проекта:

```powershell
.\start-docker.ps1
.\stop-docker.ps1
```

Первый запускает весь прототип, второй останавливает контейнеры без удаления сохранённых данных.

SQLite хранится в Docker volume `compass-data` и не удаляется при обычном перезапуске контейнеров. Сгенерированный локальный ключ хранится отдельно в volume `compass-key`.

## Что реализовано

- врач: единая карточка, динамика, связь назначения с самочувствием, история болезни, журнал приёмов, переносимость и алерты, календарь и справочник препаратов;
- пациент: ежедневная отметка, скрининг GAD-7, игровые серии и награды, графики, запись к врачу, карточки врачей, напоминания, обратная связь и жалобы на побочные эффекты;
- AI-ассистент намеренно не добавлен;
- справочник и клинические подсказки имеют демонстрационный характер и требуют проверки медицинским редактором перед реальным применением.

## Первый запуск и добавление пользователей

База после установки пустая — заранее созданных врачей и пациентов нет.

1. Откройте `http://localhost:5173`, нажмите «Я новый врач — зарегистрироваться» и создайте профиль врача.
2. Откройте `http://localhost:5174`, нажмите «Я новый пациент — зарегистрироваться», заполните данные и выберите созданного врача.
3. После регистрации пациент автоматически появится в кабинете выбранного врача.
4. Приём можно добавить как из кабинета врача, так и из раздела «Запись» пациента. Занятые слоты недоступны, а повторная запись блокируется на уровне базы.
5. Раздел «Чат» доступен в обоих кабинетах. Уведомления открываются кнопкой с колокольчиком и отмечаются прочитанными при открытии.

Для добавления ещё одного врача или пациента выйдите из текущего профиля и снова выберите регистрацию. В текущем прототипе самостоятельная регистрация открыта; перед публикацией потребуется отдельная роль администратора или система приглашений для врачей.

## Шифрование данных

Чувствительные документы хранятся в `secure_records` как зашифрованный JSON. Для каждой записи создаётся новый случайный 12-байтовый nonce, а шифрование и проверка целостности выполняются AES-256-GCM. В открытом виде остаются только технические поля для выборки: идентификатор пациента, тип записи, дата, статус и уровень алерта.

При локальном старте API автоматически создаёт 256-битный ключ в `backend/data/.data_encryption_key`; Docker сохраняет его в отдельном `compass-key`. Не добавляйте этот ключ в Git. Потеря ключа означает потерю доступа к данным, поэтому резервные копии базы и ключа должны храниться раздельно и защищённо.

Для production задайте один из вариантов:

- `DATA_ENCRYPTION_KEY_FILE=/run/secrets/data_encryption_key` — предпочтительный путь к Docker Secret/Vault secret;
- `DATA_ENCRYPTION_KEY` — base64-представление ровно 32 случайных байтов;
- `DATA_ENCRYPTION_KEY_PATH` — путь к постоянному защищённому файлу, если менеджер секретов пока недоступен.

Смена ключа без процедуры ротации сделает старые записи нечитаемыми. Само шифрование поля не заменяет TLS, аутентификацию, ролевой доступ, аудит, политику резервных копий и юридические меры.

## Согласия пациента

При регистрации пациент отдельно принимает обработку обычных персональных данных, обработку данных о здоровье, предоставление врачебной тайны выбранным врачам и пользовательское соглашение. Для пациента младше 18 лет форма дополнительно запрашивает сведения о законном представителе. Существующим пациентам экран согласий показывается при следующем входе.

Версия, хеш текста, время, IP, User-Agent и способ подтверждения сохраняются в зашифрованной записи. Шаблонные реквизиты оператора находятся в `LEGAL_OPERATOR` в `backend/app.py`; перед реальной эксплуатацией их необходимо заменить, увеличить версию `LEGAL_DOCUMENT_VERSION` и провести юридическую проверку. Чекбоксы pet-проекта не следует считать заменой электронной подписи или информированного добровольного согласия на конкретное медицинское вмешательство.

## Публикация на VPS

В репозитории есть production-конфигурация с двумя доменами и автоматическим HTTPS через Caddy:

- `doctor.example.ru` — кабинет врача;
- `patient.example.ru` — кабинет пациента;
- API не публикуется отдельным портом и доступен через `/api` каждого интерфейса.

Для демонстрационного стенда достаточно VPS с Linux, Docker Compose, 2 vCPU, 4 ГБ памяти и диском от 30 ГБ.

1. Купите домен и VPS с публичным IPv4-адресом.
2. Создайте две DNS-записи типа `A`: `doctor` и `patient`, обе направьте на IP сервера.
3. Установите на сервер Docker Engine и Docker Compose по официальной инструкции Docker.
4. Скопируйте проект на сервер, например в `/opt/clinical-compass`.
5. Создайте production-файл окружения:

```bash
cp .env.production.example .env.production
```

6. Укажите реальные домены и сгенерируйте два разных секрета:

```bash
openssl rand -hex 32
openssl rand -base64 32 | tr '+/' '-_' | tr -d '\n'
```

Первое значение запишите в `FLASK_SECRET_KEY`, второе — в `DATA_ENCRYPTION_KEY`. Файл `.env.production` нельзя добавлять в Git или передавать вместе с резервной копией базы.

7. Разрешите входящие соединения на порты `80/tcp` и `443/tcp`, затем запустите проект:

```bash
docker compose --env-file .env.production -f docker-compose.production.yml up -d --build
docker compose --env-file .env.production -f docker-compose.production.yml ps
```

Caddy самостоятельно выпустит и будет продлевать TLS-сертификаты. Домены должны уже вести на сервер, а порты 80 и 443 не должны быть заняты другой программой.

Обновление выполняется из каталога проекта:

```bash
git pull
docker compose --env-file .env.production -f docker-compose.production.yml up -d --build
```

SQLite хранится в постоянном Docker-томе `compass-data`. Резервные копии базы и `DATA_ENCRYPTION_KEY` необходимо хранить раздельно и регулярно проверять восстановление.

Это конфигурация для демонстрационного прототипа. Перед использованием с настоящими медицинскими данными нужны как минимум закрытая регистрация врачей, подтверждение учётных записей, MFA, восстановление доступа, журнал аудита, ограничение попыток входа, политика резервного копирования, мониторинг, проверка безопасности и юридическая оценка обработки медицинских данных.
